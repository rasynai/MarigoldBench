## Section-by-section notes

**Abstract (lines 16–30).** LMs now outperform average humans on many tasks, making challenging realistic evals hard to build. SciCode: scientist-curated coding benchmark with input from scientists and AI researchers in 16 natural-science subfields (math, physics, chemistry, biology, materials science). 338 subproblems decomposed from 80 main problems; optional scientific-background descriptions; scientist-annotated gold solutions and test cases. Headline: Claude3.5-Sonnet, best of those tested, solves only 4.6% of problems in the most realistic setting.

**§1 Introduction (lines 31–160).** Benchmarks saturate quickly (GLUE, GSM8K etc. cited), creating gaps between perceived and actual capability; synthetic-hard benchmarks (subsampling unsolved instances, augmentation) may not reflect real applications. SciCode's design choices: (a) natural-science focus (computational mechanics, quantum info/computing, quantum chemistry, ecology, molecular modeling); (b) abundant high-quality data not usually available to LMs; (c) all problems including gold solutions and test cases annotated, revised, verified by at least two senior researchers (PhD student level or above) in the domain; (d) realistic/current problems from everyday research tasks or influential papers; (e) zero overlap with publicly available datasets to prevent contamination; (f) tests comprehensive capability: knowledge recall + decomposition + integration; (g) toggleable setups (background on/off, gold vs generated prior solutions). Footnote 2 admits: most problems were too challenging for even the best models, so they "often simplify problem settings and provide more background during revisions." Figure 1 shows the Haldane-model decomposition example. Results preview: standard setup — Claude3.5-Sonnet 4.6% main problems; Claude3-Opus and GPT-4o 1.5%; best open model Deepseek-Coder-v2 3.1%; Llama-3-70B-Instruct and Mixtral-8x22B-Inst solve zero main problems; with background best model reaches only 12.3%.

**§2 SciCode overview (lines 161–165).** Roadmap for §2.1–2.4.

**§2.1 Challenging and realistic scientific coding problems (lines 166–190).** Sourced mainly from scripts scientists use in everyday workflows, many used in publications; primarily internal, seldom open-sourced, poorly annotated — hence low LM-training-data exposure. 80 main problems / 338 subproblems; median 3 subproblems per main problem, max 15. Split: 15 main (50 sub) dev, 65 main (288 sub) test; dev covers all five domains, over half of dev problems have <4 subproblems for easier few-shot settings. Table 1 subfield counts (main problems): Math — Numerical Linear Algebra 8, Computational Mechanics 5, Computational Finance 1; Physics — Condensed Matter 13, Optics 10, Quantum Information/Computing 6, Computational Physics 5, Astrophysics 2, Particle Physics 1; Chemistry — Quantum Chemistry 5, Computational Chemistry 3; Biology — Ecology 6, Biochemistry 1, Genetics 1; Material Science — Semiconductor Materials 7, Molecular Modeling 6. Figure 2 distributions: main problems Math 18% / Physics 46% / Chemistry 10% / Material Science 16% / Biology 10%; subproblems Math 10% / Physics 49% / Chemistry 16% / Material Science 17% / Biology 8%.

**§2.2 Main problem with multiple subproblems (lines 191–218).** Mirrors scientists' natural decomposition workflow. Main problem defines overall objective with docstring specifying inputs/outputs; subproblems are smaller parts with detailed docstrings, enabling granular evaluation. Model must implement one Python function per subproblem, then integrate into the full solution.

**§2.3 Data annotation (lines 219–285).** Three stages. **§2.3.1 Problem selection:** problems requiring intense scientific knowledge/reasoning, focused on (i) numerical methods, (ii) simulation of systems, (iii) scientific calculation (post-processing transformations). Includes problems built on Nobel-winning work: SCF for DFT (Chemistry 1998), PMNS matrix for neutrino oscillation in matter (Physics 2015), Haldane model / anomalous quantum Hall effect (Physics 2016), optical tweezer simulations for microscopic thermodynamics (Physics 2018), replica method for spin glasses (Physics 2021). **§2.3.2 Evaluation design:** annotators restricted to widely adopted packages (NumPy, SciPy, SymPy; Fig 4). Two-part test suite: (1) numerical tests = input–output pairs comparing generated code outputs to ground truth; (2) domain-specific test cases extracted from real workflows that reproduce published results or match analytical solutions — e.g., 2D square Ising phase transition at kT/J ≈ 2.269 (Onsager), surface plasmon mode in a 2D layered electron gas, ballistic Brownian motion in optical tweezers. **§2.3.3 Problem validation (3 rounds):** (1) in-domain: at least two same-domain scientists cross-check question design, solution code, domain tests; designers iterate on feedback; (2) out-of-domain: one scientist from a different field reviews clarity and information sufficiency (e.g., all constants given); (3) GPT-4 validation: feed validated subquestions to GPT-4, scientists do error analysis of its generations and redesign numerical test cases if necessary to prevent false positives, possibly revising the workflow a third time to remove ambiguity.

**§2.4 Various types of evaluations (lines 286–315).** Toggles: (a) without vs with scientist-written background (without = tests inherent knowledge+reasoning+coding; with = shifts focus to coding and instruction-following); (b) gold vs generated solutions to previous subproblems (generated = realistic, harder via error accumulation); (c) main vs subproblem level — main problem counts as solved only when ALL subproblem solutions are correct AND the integrated main solution is correct (non-compensatory). "Standard setup" = no background + generated carry-over, "closest to scientists' real use case."

## Benchmark anatomy

- **N items:** 80 main problems decomposed into 338 subproblems; test split 65 main / 288 sub, dev split 15 main / 50 sub. Median 3 subproblems per main, max 15. 5 fields, 16 subfields; physics is 46% of mains and 49% of subs.
- **Construction method:** hand-authored by scientist annotators from their own everyday research scripts (many used in publications, seldom open-sourced), plus problems reproducing influential/Nobel-winning methods. Standardized format: main problem + docstring, subproblem chain with per-step docstrings, declared dependency whitelist, optional scientist-written background per subproblem.
- **Who authored:** the paper's own author list — ~18 "data curation" scientist co-authors from UIUC, Argonne, UChicago, MIT/Harvard, Stanford, UT Austin, UNC, etc.; all problems verified by at least two senior researchers (PhD-student level or above) in the represented domain.
- **Validation/review:** three rounds — (1) >=2 in-domain scientists cross-check design/solution/tests; (2) 1 out-of-domain scientist checks clarity and information sufficiency; (3) GPT-4 generates solutions, scientists error-analyze and redesign numerical tests to prevent false positives, with a possible third workflow revision. No inter-annotator agreement statistics reported.
- **Human baseline:** none. Gold solutions define correctness, but no human pass-rate is measured anywhere in the paper.
- **Contamination defenses:** curation-time only — problems chosen to have "zero overlap with publicly available datasets"; sourced from private internal scripts (one reference is an unsubmitted manuscript). No overlap-detection procedure is described, and nothing protects the benchmark post-release (data and code are public on GitHub/leaderboard site).
- **Scoring:** execution-based, no LLM judge. Pass@1 against numerical input–output test cases plus domain-specific test cases; main problem passes only if every subproblem is correct and the integrated main solution is correct (strictly non-compensatory). Numerical tolerance policy not specified in the paper.
- **Judge design:** none (GPT-4 appears only inside the validation loop, not at eval time).
- **Statistical reporting:** none. Single pass@1 numbers to one decimal; no confidence intervals, no repeats/variance, no significance tests, no clustering by field or problem, no decoding parameters (temperature etc.), no cost/token reporting. On the 65-problem test set the main-problem percentages correspond to raw counts: 1.5%=1, 3.1%=2, 4.6%=3, 7.7%=5, 9.2%=6, 12.3%=8 problems solved.

## Limitations

**Admitted by the authors (there is no dedicated Limitations section; these are scattered):**
- Footnote 2: most problems were too challenging for even the best models, so annotators "often simplify problem settings and provide more background during revisions" — i.e., measured difficulty was deliberately tuned down, and the benchmark's difficulty is partly an artifact of where they stopped simplifying.
- Long-context degradation: performance declines when conditioning on more than 9 previous gold solutions (Fig 3), with an unexplained anomaly at 7.
- Open models improve less from background, which they attribute (hedged: "might indicate") to weaker instruction following.
- Background-provided mode shifts what is measured (coding/instruction-following rather than scientific knowledge) — acknowledged as a design property rather than a flaw.

**Observed, not admitted:**
- No statistical machinery at all: single-run pass@1, no CIs, no repeats, no significance tests. Main-problem claims rest on 0–8 successes out of 65; the headline model ranking (4.6% vs 1.5%) is a 3-vs-1 count difference and is not significant.
- No human expert baseline — "research-level" difficulty is asserted via provenance, never demonstrated by expert pass rates or time-to-solve; some failures could reflect under-specified prompts rather than missing capability.
- GPT-4 in the validation loop biases the benchmark: tests were redesigned specifically where GPT-4 produced false positives, and workflows revised where GPT-4 revealed ambiguity — an asymmetric adversarial-filtering pressure relative to the GPT-4 family that muddies cross-model comparisons.
- Contamination defense is curation-time only; the dataset, gold solutions, and tests are publicly released (GitHub link on page 1), so the "zero overlap" property decays immediately for future models, and no canary strings, held-out regeneration, or overlap-scanning procedure is described.
- No detail on numerical-test tolerances, number of test cases per (sub)problem, or how the "integrated main solution" test differs from the last subproblem's test; false-positive/false-negative rates of the harness are unquantified.
- Decoding configuration (temperature, top-p, max tokens), API snapshot dates for most models, and evaluation cost are unreported — pass@1 without decoding parameters is not reproducible.
- Skewed domain mix (physics 46% of mains; single-problem subfields like Computational Finance, Particle Physics, Biochemistry, Genetics) makes per-field claims impossible; correlated failures within a subfield are never modeled.
- Subproblem-level scores under generated carry-over are contaminated by upstream errors (a subproblem can fail because step 1 was wrong), yet Table 2/3 subproblem columns are presented as if per-step skill; only Fig 3 partially disentangles this.
- Non-compensatory main metric plus 65 items compresses the score range so much that the benchmark cannot distinguish today's models from each other — only from zero.

## Implications for CRUCIBLE-CHAIN

1. **Scale: grow independent templates before instances, and size for ~400+ effective items.** SciCode's cautionary math: 65 test chains means every main-problem percentage is a count of 0–8, and the headline gap (4.6% vs 1.5%) is 3 vs 1 successes — unresolvable (Wilson 95% CI for 3/65 ≈ [1.6%, 13%]). For CRUCIBLE-CHAIN's target regime (single-digit pass rates), distinguishing e.g. 4% from 10% at alpha=0.05 / power 0.8 needs roughly 300–450 items per model — but only if items are independent. With 8 templates x 18 instances, within-template correlation means the effective sample size is nearer the number of templates; cluster-robust inference is unstable below ~30–40 clusters. Actionable: expand to >=30 independent templates (SciCode's 16 subfields x 80 problems was still too few and they never even modeled the clustering), report by-template cluster bootstrap CIs, and use paired tests (McNemar on shared instances) for model-vs-model claims.

2. **Fix the saturation leak the way SciCode's standard setup does: make recipe-withholding the scored condition and recipe-provision a diagnostic toggle.** CRUCIBLE-CHAIN saturated at 94–100% because prompts leaked method recipes and answer menus. SciCode quantifies exactly this: providing scientist-written background (the method recipe) moved main-problem pass from 4.6% to 12.3% (Claude3.5-Sonnet) and subproblem pass by +9 to +11 points — and their without-background prompt still forces the model to write its own background first, which is gradable evidence of method choice. Actionable: define the scored condition with no method names, no formula menus, no enumerated answer options; keep a background-provided condition as a separate diagnostic axis and publish the delta as the benchmark's "leakage value" so any future prompt regression is detectable.

3. **Chain length alone will not produce single-digit pass rates — stages must have decorrelated failure modes.** SciCode: 26% subproblem pass with median only 3 stages yields 4.6% main pass; naive independence (0.26^3 ≈ 1.8%) underpredicts because successes correlate within a problem (a model that knows the Haldane model tends to get all its stages). CRUCIBLE-CHAIN's 5–8 stages will likewise compress less than p^s if stages share one skill. Actionable: audit per-template stage-pass correlation matrices from the saturation-run logs; redesign stages so each hinges on a different judgment call (method selection, defect detection, unit/convention choice, premise audit), and verify the attractive wrong path is actually taken at non-trivial rates per stage in pilot runs.

4. **Score chains with generated carry-over as the primary metric, and run a gold-conditioned ablation to localize failure.** SciCode dubs "generated solutions carried forward" the standard setup because it matches real use and adds error accumulation; its Fig 3 gold-conditioning curve then localizes ability by stage depth, and finds degradation only past 9 prior steps — so CRUCIBLE-CHAIN's 5–8-stage chains are safely below the long-context cliff and any failure can be attributed to judgment, not context management. Actionable: implement both modes in the harness; report stage-conditional pass (given gold prefix) per stage index as the diagnostic that says *which* stage kills chains, and use it to prove the planted-defect stage (not context length) is the discriminator.

5. **Adopt SciCode's round-3 false-positive audit, aimed at your own graders.** Even with constructed truth and near-zero label error, the risk is wrong-reason passes (a shortcut that emits the right number without the right judgment) and grader false positives. SciCode explicitly ran GPT-4 against every problem and "redesign[ed] the numerical test cases if necessary to prevent false positives" — but by using one model family they biased difficulty against it. Actionable: run >=3 frontier model families against every template; manually audit every PASS in the planted-defect and flawed-premise conditions for shortcut reasoning; where a stage can be passed by an answer-menu guess or a default-parameter fluke, add a second orthogonal probe of the same judgment (e.g., require the detected defect to be named and quantified, not just a final number). Symmetrically, audit refusal-correct items so that blanket refusal heuristics don't score as competence.

6. **Exploit the generator advantage SciCode lacks: regenerate test instances per evaluation cycle.** SciCode's contamination story ("zero overlap with publicly available datasets," problems from unpublished internal scripts — one reference is literally an unsubmitted manuscript) is strong exactly once, then decays on release, and they released everything. CRUCIBLE-CHAIN's deterministic generator can make contamination structurally irrelevant. Actionable: publish the generator and a frozen dev split only; keep test-instance seeds private; regenerate fresh instances (new parameter draws, new planted-defect locations) for every leaderboard run; log seeds for auditability. Also copy SciCode's footnote-2 lesson in reverse: version the benchmark explicitly (1.x hardening) rather than quietly re-tuning difficulty when models fail or saturate.

7. **Add the two baselines SciCode omitted: human experts and reported uncertainty.** SciCode's "research-level" claim rests on provenance, not on any measured human pass rate, and its results table has no error bars, no repeats, and no decoding parameters. For a benchmark whose thesis is "frontier models fail on judgment chains," a skeptic's first objection is ill-posedness. Actionable: run 2–3 domain-competent humans (with the same tooling budget) on a stratified subsample of ~1–2 instances per template to establish expert solvability per condition (including that experts do refuse on flawed premises); pre-register k repeats per item (k>=3 at fixed temperature) and publish mean pass@1 with cluster-bootstrap CIs plus the full decoding config and per-run cost, making every claimed model gap checkable.
