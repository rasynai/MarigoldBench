## Section-by-section notes

**Abstract.** Introduces MLE-bench: 75 ML-engineering competitions curated from Kaggle; human baselines from Kaggle's public leaderboards; open-source scaffolds used to evaluate frontier LMs. Best setup, o1-preview + AIDE, "achieves at least the level of a Kaggle bronze medal in 16.9% of competitions." Also studies resource scaling and pre-training contamination. Code at github.com/openai/mle-bench.

**1 Introduction.** Motivation: coding benchmarks are saturating but few measure autonomous end-to-end ML engineering. Design goals: (i) challenging, representative tasks; (ii) comparability to human-level performance. Total prize value across the 75 competitions: $1,948,016 ($25,974 average). Framed as a measure for model autonomy in OpenAI's Preparedness Framework, Anthropic's RSP, and GDM's Frontier Safety Framework. Headline: o1-preview+AIDE medals in 16.9% of competitions (pass@1), doubling to 34.1% at pass@8; GPT-4o goes 8.7% (24 h) to 11.8% (100 h). Key qualitative finding: agents do well on well-known-approach competitions but "struggle to debug issues and recover from missteps." Four listed contributions: the benchmark (75 tasks "carefully handcrafted by a team of ML engineers"), large-scale evaluations, resource-scaling experiments, contamination/plagiarism experiments.

**2 MLE-bench.** 75 tasks manually sourced from Kaggle to reflect "day-to-day skills that ML engineers use in frontier labs." Kaggle context: leaderboards, bronze/silver/gold medals.

**2.1 Dataset curation.** Each sample = scraped description (Overview + Data tabs) + dataset (mostly with a new train-test split) + locally runnable grading code + a leaderboard snapshot. Funnel: 5,673 completed Kaggle competitions (Meta Kaggle, accessed 2024-05-15) → exclude Community Competitions → 586 manually screened for relevance → 75 selected (screening criteria in A.1). Manual annotation of problem type and complexity: Low (<2 h for an experienced ML engineer to produce a sensible solution, excluding training time), Medium (2–10 h), High (>10 h). Split: 22 Low (30%), 38 Medium (50%), 15 High (20%) — note Figure 6's caption instead says 29%/51%/20%. Plus 7 extra competitions as a development split. New test splits are typically 10% of the original train set, checked so the sample submission scores similarly on original vs reconstructed test sets; grading logic re-implemented per competition from the described metric (AUROC to domain-specific losses).

**2.2 Metrics.** Uses the Private (not Public) leaderboard because submissions overfit the Public one; snapshots taken May–August 2024. Medal thresholds vary by team count (Table 1: e.g., bronze = top 40% for <250 teams, top 10% for 1000+ teams; gold = top 10 + 0.2% for 1000+, threshold +1 per 500 additional teams). Medal logic applied to all competitions even where Kaggle didn't award medals. Headline metric: % of attempts achieving any medal — "designed to be a challenging metric"; only nine humans have ever earned medals on 75 different competitions (the nine Kaggler usernames are listed in footnote 5). Raw scores also reported but hard to aggregate.

**2.3 Setup.** Method-agnostic; only a CSV submission is graded. Developers should disclose models, scaffolding, internet access, hardware, runtime, and any inclusion of Kaggle solutions in prompts. A local validation server checks submission validity (unlimited use, no score returned), mirroring Kaggle's 5-submissions/day check.

**2.3.1 Rules.** Submissions must be produced by a model separate from the agent (no hand-writing predictions from world knowledge — an explicit anti-memorization rule); viewing others' solutions is forbidden. Rule-breaking detection: a GPT-4o-based log-inspection tool (details A.3). Plagiarism detection: Dolos comparing submitted code against the top 50 notebooks per competition; similarity >60% disqualifies and flags for review.

**3 Experiments and Results.** Environment: Ubuntu 20.04 Docker on a secure cluster; 24 h per competition; 36 vCPUs, 440 GB RAM, 4095 GiB SSD, one 24 GB Nvidia A10 GPU; 3 seeds default (mean ± standard error), with exceptions noted.

**3.1 Main experiment.** Scaffold comparison with GPT-4o (gpt-4o-2024-08-06): AIDE 8.7 ± 0.5% any-medal vs MLAB 0.8 ± 0.5% and OpenHands 4.4 ± 1.4% despite similar valid-submission rates; AIDE is Kaggle-purpose-built. Model comparison under AIDE: o1-preview 16.9 ± 1.1% (16 seeds), GPT-4o 8.7 ± 0.5% (36 seeds), Claude 3.5 Sonnet (20240620) 7.6 ± 1.8%, Llama 3.1 405B 3.0 ± 1.0% (3 seeds each). Full Table 2 details: o1-preview made a submission 98.4 ± 0.4%, valid 82.8 ± 1.1%, above median 29.4 ± 1.3%, bronze 3.4 ± 0.5%, silver 4.1 ± 0.6%, gold 9.4 ± 0.8%. o1-preview averages 7 gold medals — vs 5 golds needed for Kaggle Grandmaster — with explicit caveats (not all chosen competitions are medal-granting; modified datasets/grading; agents use newer technology than original participants). Gemini-1.5-Pro-002 could not be evaluated: API calls "repeatedly blocked due to model outputs being flagged for recitation" (footnote 7). Discussion: agents often failed to create valid submissions and did not always use the validation server; MLAB/OpenHands end runs early (sometimes within minutes); AIDE keeps prompting until 24 h or 500 nodes (text says 500 max; Table 7 lists agent.steps = 2000 — an apparent inconsistency); small scaffold details matter (MLAB filled its context by reading long files); all agents failed to factor in compute/time limits (overloading disk/RAM, killed processes) and "rarely verbalized any consideration of how long their produced code would run for."

**3.2 Increasing number of attempts.** pass@k estimator from Chen et al. 2021 (unbiased combinatorial form, drawn from n seeds). GPT-4o (AIDE) pass@6 = 17.0% ≈ o1-preview pass@1 = 16.9%; both agents' pass@6 roughly double their pass@1; o1-preview reaches 34.1% at pass@8 (from §1).

**3.3 Varying compute.** GPT-4o (AIDE) on CPU-only 9.1 ± 1.0%, Standard (one A10) 8.7 ± 0.5% (36 seeds), Extra GPU (two A10s) 10.2 ± 2.0% (3 seeds) — statistically indistinguishable; manual log review found no attempt to use the second GPU. Kaggle itself gives users a free 16 GB P100.

**3.4 Increasing time.** 100-hour runs with max nodes raised 10× to 5,000; hourly snapshots graded. GPT-4o (AIDE): most medals earned in the first couple of hours, slow accumulation after; 8.7% at 24 h → 11.8% at 100 h (number from §1). Medal counts sometimes *decrease* over time because AIDE's method for selecting its "best" attempt is imperfect.

**4 Contamination & plagiarism.** Adopts Dekoninck et al.'s definition (artificially inflated, non-generalizing performance). Main worry: solutions derived from public competition write-ups. Overall finding: "Our experiments find no evidence of results being systematically inflated due to memorization." Plagiarism detector on all medal-winning submissions: no plagiarism (A.4). Log-analysis tool + manual inspection of flags: no rule-breaking (A.3).

**4.1 Familiarity with top solutions.** Familiarity := mean token probability GPT-4o's *base model* assigns to a document (mean over the competition page + 5 most popular discussion posts, typically winners' write-ups), following Carlini et al. 2023. Performance normalized between sample-submission score and gold-medal score. Result (Figure 5): Pearson r = −0.24, p = 0.04 — i.e., no *positive* familiarity-performance relationship (the point estimate is actually negative and nominally significant).

**4.2 Obfuscating competition descriptions.** All 75 descriptions manually rewritten to hide provenance (remove Kaggle references, competition names, non-essential text) while retaining key information; GPT-4o (AIDE), 10 seeds: obfuscated 8.4 ± 1.0% vs original 8.5 ± 0.6% — no significant difference. Authors' caveat: "This does not rule out subtler effects of contamination."

**5 Related work.** Coding benchmarks (HumanEval, APPS, MBPP, LiveCodeBench) saturating (AgentCoder 96.3% HumanEval, 91.8% MBPP — footnote 12) yet SWE jobs are not automated; SWE-bench progress rapid, motivating early measurement. Versus MLAgentBench: 13 tasks with provided baseline solutions, scored as ≥10% improvement over baseline; MLE-bench is bigger, harder, from-scratch. Versus ML-Bench: repository-use, not open-ended development. Versus Weco AIDE's claim of beating >50% of humans: state-of-the-art models surpass MLE-bench's median only ~10% of the time — evidence MLE-bench's competition selection is harder. Versus DSBench (concurrent): template-automated task creation excludes non-standard competitions; MLE-bench ports each manually. Agent-evaluation context: AgentBench, GAIA (466 questions), AgentQuest, Kapoor et al.

**6 Limitations.** (1) Contamination & plagiarism: models may have trained on all public Kaggle material, including test sets (footnote 13: GPT-4 base reproduced several rows of the Titanic dataset from a few-row prompt); mitigations catch code plagiarism/label recall but "it is difficult to detect the reuse of high-level strategies"; no guarantees for future models; suggests regularly refreshing with new competitions. (2) Coverage of AI R&D: MLE-bench selects clean, well-specified problems with clear metrics; real R&D often lacks a problem statement, and dataset/metric design is part of the work; still covers core competencies (multi-modal data prep, long-running training scripts, debugging weak models). (3) Differences from real competitions: new splits and re-implemented grading raise comparability concerns (mitigated by distribution checks and sample/gold submission consistency); algorithmic progress makes older competitions easier for today's agents; complexity labels may need updating. (4) Accessibility: one full run = 24 h × 75 = 1,800 GPU-hours; o1-preview (AIDE) used 127.5M input + 15.0M output tokens per seed of 75 competitions.

**7 Conclusion.** Restates design (direct agent-vs-human comparison in a simulated Kaggle), headline result (16.9%), open-sourcing, and safety motivation.

**Ethics statement.** Automated ML research could accelerate science but also enable models to improve their own training code faster than human oversight can track; "We believe a model capable of solving a large fraction of MLE-bench likely possesses the capability to execute many open-ended ML tasks." Open-sourcing for transparency into acceleration risks; public data only; licenses respected via reproduction code.

**Reproducibility statement.** Full details and code public; agent-running infrastructure code is infra-specific and excluded but examples are provided; compute/token costs are a practical barrier.

**References.** Standard; notable anchors: Chen 2021 (pass@k), Carlini 2023 (memorization/familiarity), Dekoninck 2024 (contamination definition), Maertens 2024 (Dolos), Jimenez 2024 (SWE-bench), Huang 2024b (MLAgentBench), Schmidt 2024 (AIDE), Wang 2024 (OpenHands), Jing 2024 (DSBench).

## Benchmark anatomy

- **N items:** 75 Kaggle competitions (22 Low / 38 Medium / 15 High complexity) + a 7-competition development split. One "item" is an entire multi-hour engineering task, not a question.
- **Construction:** manual curation funnel 5,673 → 586 (excluding Community Competitions; manual relevance screen) → 75. Each competition ported by hand: description scraped, new train/test split built (default 10% test from original train; grouped/temporal splits where leakage demanded), grading code re-implemented from the stated metric. "Carefully handcrafted by a team of ML engineers."
- **Item authors:** original Kaggle competition organizers (external); the OpenAI team authored the ports, splits, grading code, complexity/category annotations, and obfuscated rewrites.
- **Validation/review:** each competition screened by ≥2 ML engineers at leading AI companies against 9 explicit criteria (A.1); split fidelity checked by requiring the sample submission to score similarly on original vs reconstructed test sets; sample and gold submissions confirmed consistent with the human leaderboard.
- **Human baseline:** entire Kaggle Private leaderboards (snapshots May–Aug 2024) — thousands of real human teams per competition — with Kaggle's team-count-dependent medal thresholds (Table 1) applied uniformly. Anchor for the headline metric's ceiling: only nine humans have ever medaled in 75+ competitions.
- **Contamination defenses:** (a) rule that a model separate from the agent must produce predictions (blocks label recall); (b) GPT-4o log-analysis judge with 3-question rubric + human review of flags; (c) Dolos code-similarity vs top-50 notebooks, 60% disqualification threshold + human review; (d) familiarity analysis (base-model token probabilities vs performance: r = −0.24, p = 0.04); (e) obfuscated-descriptions A/B (8.5 ± 0.6 vs 8.4 ± 1.0); (f) explicit disclosure norms for anyone reporting on the benchmark. Admitted residual risk: reuse of high-level strategies is undetectable; datasets themselves are public and memorizable (Titanic rows reproduced by GPT-4 base).
- **Scoring:** deterministic, competition-specific grading code on a submitted CSV; no LLM judge in the score path (LLM judges only police rules). Headline = % attempts achieving any medal; secondary = valid-submission %, above-median %, bronze/silver/gold %, raw scores. Binary thresholding against human leaderboards makes scores human-anchored and non-gameable by partial credit.
- **Statistical reporting:** mean ± SEM over seeds — 3 seeds default, 16 for o1-preview (AIDE), 36 for GPT-4o (AIDE), 10 for the obfuscation run. Unbiased pass@k estimator (Chen et al. 2021). One Pearson correlation with p-value (familiarity). No confidence intervals beyond ±1 SEM, no competition-level clustering or hierarchical modeling, no between-model significance tests, no multiple-comparison control. Uncertainty is run-to-run variance over a *fixed* 75-task set, so it excludes task-sampling uncertainty entirely.

## Limitations

**Admitted by authors (Section 6 and elsewhere):**
1. Contamination: all Kaggle material (including test sets) may be in pre-training; GPT-4 base reproduced Titanic rows; detection covers plagiarism/label-recall but not high-level strategy reuse; no guarantees for future models; refresh with new competitions suggested.
2. Coverage: tasks are clean, well-specified, single-metric — unlike real AI R&D where problem definition is the work.
3. Comparability to humans: new splits + re-implemented grading; today's agents wield newer tech than the original human contestants; complexity labels will drift.
4. Cost/accessibility: 1,800 GPU-hours + hundreds of millions of tokens per full run.
5. Scaffold imperfections acknowledged: fixed obvious failures "but expect failure modes to remain"; AIDE's best-attempt selection is imperfect; validation server underused by agents.
6. Familiarity/obfuscation experiments "do not rule out subtler effects of contamination"; contamination checks were run only for GPT-4o.

**Observed, not admitted:**
1. **No task-sampling uncertainty:** SEM is over seeds on a fixed 75-competition set. Claims like "16.9 ± 1.1%" quantify run noise only; the benchmark-composition uncertainty (would the ranking survive a different draw of 75 competitions?) is never estimated — no bootstrap over competitions, no clustered SEs, despite per-competition binary outcomes being the natural unit.
2. **No significance tests for any headline comparison** (o1 vs GPT-4o, AIDE vs MLAB, CPU vs GPU): differences are eyeballed against overlapping/non-overlapping SEMs; the 3-seed conditions have very wide SEs (e.g., Extra GPU 10.2 ± 2.0).
3. **Internal inconsistencies:** Table 9's overall any-medal column disagrees with Table 2 for MLAB (1.3 vs 0.8) and OpenHands (5.1 vs 4.4) and slightly for others (8.6 vs 8.7; 3.1 vs 3.0; 7.5 vs 7.6) with no explanation; §2.1 says 30% Low while Figure 6's caption says 29%; §3.1 says AIDE max 500 nodes while Table 7 says agent.steps 2000 (and §3.4's "10x to 5,000" is consistent with 500).
4. **Judge unreliability quantified but not propagated:** the GPT-4o-mini rules judge produced up to 14.1% false-positive flag rates; all flags were human-adjudicated here, but third parties running the open-sourced tool will inherit an unreliable judge, and false *negatives* are never estimated.
5. **Contamination tests are underpowered and indirect:** the obfuscation A/B (10 seeds, SEs ±0.6/±1.0 on a base of ~8.5%) could not detect a contamination effect smaller than a few points; familiarity uses GPT-4o's base model as a proxy even for conclusions about other models; the significant *negative* correlation (r = −0.24, p = 0.04) is likely confounded (popular/old competitions are easier to memorize but also may be harder to medal in, or vice versa) and is waved through as "no positive relationship."
6. **Human baseline skew:** leaderboards include many casual entrants (medals are top-N%, so "above median" is a weak bar); conversely, medal thresholds are computed against contemporaneous humans who lacked 2024 tooling — the direction of net bias is unknown and unmeasured.
7. **Fixed-scaffold confound:** model comparison is entirely within AIDE, whose feedback model is pinned to GPT-4o for all target models — cross-model results are partially mediated by an OpenAI model in the loop (acknowledged only as "minimal effect" in a footnote, untested).
8. **Selection effects:** the 9 curation criteria (local metric, CSV output, same-distribution splits, no external data) systematically remove exactly the messy tasks the paper admits real R&D involves; the dev split (7 competitions) is small and its usage protocol unspecified.

## Implications for CRUCIBLE-CHAIN

1. **Count clusters, not instances, when answering the scale question of record.** MLE-bench's precision comes from 75 *independent* tasks; its ±1.1pp SEM on 16.9% required 16 seeds × 75 tasks ≈ 1,200 runs, and even then it quantifies only run noise because the task set is fixed. CRUCIBLE-CHAIN's 8 templates × ~18 instances is, for inference purposes, an 8-cluster benchmark: instances within a template share the recipe and failure mode, so effective n ≈ 8, far below anything supporting "single-digit vs 20%" claims. Action: report cluster-robust (template-level bootstrap) CIs now; to claim, e.g., 5% vs 15% separation with non-overlapping 95% CIs, target 50–75 independent templates (MLE-bench's own choice of 75 is a defensible precedent), and treat added instances-per-template as reducing only within-cluster noise.
2. **Pre-register the resource envelope; report pass@k explicitly.** MLE-bench's score doubles from pass@1 to pass@6-8 (16.9→34.1%) and rises 8.7→11.8% from 24 h→100 h, i.e., "frontier pass rate" is undefined without k, time, and token budgets. CRUCIBLE-CHAIN's "target single-digit frontier pass rates" must be stated as pass@1 under a fixed attempts/token/tool budget, with the pass@k curve published (Chen-style unbiased estimator over n repeats) so saturation claims can't be gamed by resampling. MLE-bench's repeats policy (3 seeds default, 16–36 for headline rows) is a workable template: run ≥3 repeats everywhere and 10+ on the headline configuration.
3. **Run the obfuscation A/B as a permanent condition — it is the exact experiment for CRUCIBLE-CHAIN's saturation post-mortem.** MLE-bench manually rewrote all 75 descriptions to strip provenance while keeping task-sufficient information, then measured original vs obfuscated (8.5 ± 0.6 vs 8.4 ± 1.0, 10 seeds). CRUCIBLE-CHAIN saturated because prompts leaked method recipes and answer menus — the analogous fix is a minimal-information prompt variant (no method hints, no option lists, free-form numeric/refusal answers) shipped alongside the full prompt, with the delta reported per template. If scores stay 94–100% on the stripped variant, the difficulty problem is in the tasks; if they crater, the leak was the prompt — MLE-bench shows a 10-seed A/B suffices to see multi-point deltas, but also that ±1pp effects are invisible at that n.
4. **Kill answer menus structurally, the way MLE-bench's CSV rule does.** MLE-bench never offers options: the agent must produce an open-ended artifact (predictions CSV) that is graded deterministically, and a rule forbids writing answers from world knowledge, enforced by log inspection. CRUCIBLE-CHAIN's deterministic generator enables something stronger: require the model to output the computed quantity/decision per stage in open format, regenerate instance data per release (fresh constants per evaluation run), and validate answers with the generator — making both memorization and menu-matching impossible by construction rather than by detection. Where refusal is the correct answer (flawed-premise condition), keep refusal open-ended too, or models will pattern-match a visible "refuse" option.
5. **Human-anchored, tiered headline metrics keep a hard benchmark informative across the difficulty range.** MLE-bench's headline (any medal) has a ceiling calibrated to the best humans ever (only nine people have 75+ medals), but it still reports a ladder: made-submission → valid → above-median → bronze/silver/gold. CRUCIBLE-CHAIN's non-compensatory all-stages metric is the "medal"; add the ladder below it (stages-correct distribution, first-failed-stage histogram, per-condition pass rates for clean/planted/flawed) so that a single-digit headline is decomposable and progress between 2% and 9% is measurable rather than noise. MLE-bench's Table 9/10 breakdowns (by complexity and category) are the model: report per-template and per-condition tables with SEs.
6. **Target the demonstrated failure modes when designing attractive wrong paths.** MLE-bench's qualitative findings: agents "struggle to debug issues and recover from missteps," fail to budget time/compute, underuse validation tools even when prompted, and score 0% on post-2022 competitions and on whole categories (image segmentation, object detection, LLM finetuning) while doing fine on well-known recipes. CRUCIBLE-CHAIN stages should therefore place the planted defect *downstream* of an early commitment (forcing recovery, which agents demonstrably lack) and reward checking behavior (analog of the validation server) — and the near-zero post-2022 result predicts that novel constructed tasks with no public recipe are exactly where frontier pass rates collapse, supporting the constructed-truth strategy over harder-but-familiar tasks.
7. **If any LLM judge appears anywhere (even for rule policing), calibrate it against human adjudication and publish the false-positive rate.** MLE-bench's GPT-4o-mini rules judge flagged up to 14.1% of medal-winning runs, and 100% of flags were false positives on human review. For CRUCIBLE-CHAIN, deterministic grading avoids this in the score path, but any automated screening of transcripts (e.g., detecting that a model gamed the flawed-premise condition or accessed leaked recipes) needs the same design: rubric-based LLM screen → mandatory human review of flags → publish both flag and confirmed rates.
8. **Adopt their disclosure-and-comparability discipline.** MLE-bench specifies what evaluators must report (model, scaffold, internet access, hardware, runtime, any solutions in prompts) and pins environment details (Docker image, package list, prompts in Figure 8, scaffold hyperparameters in Table 7). CRUCIBLE-CHAIN should ship an equivalent "conditions of measurement" spec — prompt text hashes, generator version, instance seeds, attempts budget — so that a reported single-digit pass rate is reproducible and a saturation claim (like the current 94–100%) can be traced to a specific prompt version; MLE-bench's Table 2 vs Table 9 mismatches show how easily unversioned aggregate numbers drift even within one paper.
